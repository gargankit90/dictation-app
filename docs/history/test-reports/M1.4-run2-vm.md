# M1.4 test report, run 2 (VM run for manual criteria 3–5)

PR: #45 at a57a325 (product code as at cd471f8)
Result: PASS

A pilot of running the `[manual]` checks in the Lume VM instead of on the
owner's Mac. Only criteria 3–5 were in scope; 1–2 are `[auto]` and covered by
run 1 and CI.

## Setup

- VM: fresh `dictation-vm` cloned from `dictation-vm-golden` (golden not
  touched), macOS 15.6.1 (24G90), arm64, 1024×768 display.
- Probe: `cargo build -p dictation-platform --example hotkey_probe` on the host
  (arm64 Mach-O), copied to the VM with `scp`. Run in the VM's Terminal from a
  `.command` file (`~/hotkey_probe | tee ~/probe.log`), so Terminal is the app
  that needs Accessibility, as on a real Mac.
- Evidence: `test-reports/M1.4-vm/`: `probe-output.log` (the whole probe output
  of all four runs, with a marker line before each step) and screenshots.

## How the VM was driven

| What | How | Synthetic or real |
| ---- | --- | ----------------- |
| Screenshots, AX tree, clicking the Terminal toggle in System Settings | `cua-driver` (the server behind the `cua-vm` MCP), spoken to over `ssh lume@<vm> cua-driver mcp` with a small JSON-RPC client | AX press |
| Password sheet when turning the toggle on ("Privacy & Security is trying to modify your system settings") | The VM's own Lume VNC endpoint (127.0.0.1, `lume get dictation-vm`), approved by the Lead for TCC/password sheets only | VNC (virtual HID) |
| Dismissing a TCC "sshd-keygen-wrapper wants to control System Events" prompt I caused with an `osascript` call (clicked Don't Allow) | Same VNC endpoint | VNC |
| Right Option, Left Option, Esc | `keypost` (`M1.4-vm/keypost.swift`): `CGEventPost` at the HID tap. Right Option = `flagsChanged`, keycode 61, flags Alternate + right-alt device bit, held 700 ms, then released; Left Option = keycode 58; Esc = keyDown/keyUp keycode 53. Run inside the VM's GUI session from a second Terminal window (Terminal holds Accessibility), fed through a FIFO over ssh | **Synthetic** |
| Focus changes (Notes, Safari, a `sudo` prompt) | `open -a …` over ssh | Real app activations |
| Revoking Accessibility | `tccutil reset Accessibility com.apple.Terminal` over ssh | Real TCC change |

The `cua-vm` MCP server itself did not connect in this session: its launcher
is pinned to `192.168.64.3`, and the fresh clone came up on `192.168.64.4`.
Talking to the same `cua-driver` over ssh worked. `cua-driver` has no
single-modifier key or press-and-hold, and `CGEventPost` from the ssh session
itself is dropped (no Accessibility), so key events had to come from a process
under Terminal. The password sheet drops `cua-driver` keystrokes, which is why
VNC was needed there.

## Findings

1. **minor:** the running probe never printed `Accessibility granted` after
   the grant was switched on in System Settings. Twice (runs A and C) the probe
   polled for 60–70 s after the toggle showed on and still waited; a Terminal
   relaunch was needed. The PR's own steps allow for this ("If macOS only
   applies the grant after a terminal restart, quit and rerun"), and criterion
   4 only asks for `PermissionMissing`, so this does not fail it. It may be
   macOS caching `AXIsProcessTrusted()` for a process whose responsible app is
   Terminal; worth checking on real hardware before the app relies on a live
   grant (onboarding in a later milestone).
2. Not run: the optional `Shift` + Right Option step and the optional
   `Ctrl+Shift+Space` Secure Input step.
3. Two marker lines in `probe-output.log` (3b, 3c) say "time not recorded":
   a quoting slip stored a literal `$(date +%T)`; the probe lines under them
   are unedited.

## Limits of this run

- All key input was synthetic (`CGEventPost` at the HID tap, inside the VM). It
  goes through the same event tap a real key does, but it is not a physical
  key on a physical keyboard.
- A VM, not the owner's Mac: no hardware keyboard, no external display.
