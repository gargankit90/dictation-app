## Correctness assessment

- Ownership remains decided by the file lock. `Instance::drop` calls `Server::stop` before unlocking; the second call through `Server::drop` is idempotent. No new socket binding or unlinking occurs outside the lock holder.
- `Shutdown::begin` and `start_delivery` use the same mutex. A valid message therefore either registers before shutdown and is included in its wait, or returns unanswered without invoking the callback. The client treats EOF/reset as retryable, so that latter path can take ownership after the lock is released.
- The delivery guard stays alive through the ACK/NAK write. This closes the reported callback-completed / process-exited-before-ACK window during normal bounded deliveries. An ACK still means the callback succeeded; a NAK still fails explicitly.
- The shutdown mutex is released before taking the callback mutex or invoking user code. The condvar releases it while waiting; completing readers can decrement the counter and notify. No new callback/shutdown mutex cycle found. Queued callbacks count as deliveries, and callback unwind releases the delivery guard.
- Silent and partial-frame peers have not registered a delivery and are not waited on. They cannot invoke the callback after observing shutdown. The wait for registered deliveries has a total limit of twice `io_timeout`, rather than a per-reader limit.
- The documented timeout fallback is real: an arbitrarily stalled callback can outlive lock release. This patch is not an exactly-once protocol under callback stalls, callback panic, process crash, or failed ACK writes. The shell callback injects events without taking the single-instance state mutex; no concrete new user-facing failure found in that path. A client ACK timeout fails explicitly instead of claiming success or retrying a possibly handled message.
