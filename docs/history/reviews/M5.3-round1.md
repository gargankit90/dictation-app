## Findings

### R1 — Major: reopening Settings keeps a stale login-item state and can undo the user's OS choice

**Location:** `src/Settings.tsx:103` (the load effect ends at line 112); related save at line 212.

The effect reads the OS login-item state only when the component mounts. The real Settings window is created hidden at startup, and closing it calls `window.hide()` instead of destroying it (`src-tauri/src/lib.rs:227`). Showing it from the tray does not remount `Settings`, and there is no focus, visibility, or tray-open refresh. Consequently even the first visible opening can show a state read much earlier.

Concrete failure: leave launch at login off in the app, hide Settings, enable the item in System Settings, and reopen Settings. The checkbox remains unchecked. Change only Language and Save: the stale `false` is submitted and `launch::apply` unregisters the app, undoing the user's external choice. In the inverse direction the stale checked value also causes an unwanted registration attempt; whether that succeeds or needs approval depends on the OS state.

**Evidence:** `/tmp/m53-review-ui/stale-login.test.tsx` imports the actual production component and mocks the typed IPC boundary. With the same component retained across focus/visibility events, the OS reports `false`, the checkbox remains `true`, and `get_settings` has been called only once. Two further tests change only Language and observe an unwanted registration or unregistration request through the mock backend. All three regression assertions fail; output is `/tmp/m53-review-ui/result.txt`. These are component tests, not a claim of GUI/VM execution.

**Suggested fix:** refresh the OS state whenever the retained Settings window is shown/focused, while preserving unsaved unrelated fields. Track an explicit login-item edit so an unrelated settings save cannot overwrite a newer OS choice. Add a test that retains the same component while simulating an external OS change; unmounting/remounting misses this bug.

### R2 — Major: a backward clock adjustment causes rotation to delete the active log

**Location:** `src-tauri/src/logging/rotation.rs:121`; filename selection starts at line 96.

`start_new` starts from wall-clock time and advances only if that exact filename already exists. It does not ensure the new name sorts after existing files. When the clock moves backward with the retention slots full, rotation creates an earlier-sorting file and `prune` immediately removes that new active file. On macOS the open handle remains writable, so logging reports success while writing to an unlinked file that Reveal log cannot show. Further rotations repeat this until the clock catches up with the retained filenames.

**Evidence:** `/tmp/m53-review-rotation.rs` directly includes the production rotation module, using its injected clock. With `max_bytes=10, keep=2`, write `first11111` at time 2000, `second2222` at 2100, then move the clock to 1900 and write `latest3333`. Both writes and flush succeed, but the directory contains only `first11111second2222`; a subsequent `fourth4444` also disappears. The same failure applies to the production five-file retention setting. Output is `/tmp/m53-review-rotation.txt`.

**Suggested fix:** choose monotonically increasing filenames relative to the newest retained file, and ensure pruning never deletes the active path. Test both a backward clock step during rotation and startup with future-dated existing logs.

### R3 — Major: reading Settings invokes a macOS 13 API on older advertised systems

**Location:** `crates/platform/src/launch/macos.rs:38`; also line 46.

Every `get_settings` now reaches `SMAppService::mainAppService()` unconditionally on macOS. `src-tauri/tauri.conf.json` does not set a minimum system version; the pinned Tauri configuration defaults to 10.13. However, `SMAppService` and `mainAppService` require macOS 13. On an older system the class lookup panics rather than returning `LaunchAtLoginError::Unsupported`; the command's blocking-task wrapper turns that into `the settings task crashed`. This prevents loading the entire Settings form, including provider/key configuration, even when launch at login is not requested.

**Evidence:** static compatibility check, not execution on an older OS. The installed SDK's `SMAppService.h:65` and `:91` mark the class and method `API_AVAILABLE(macos(13.0))`; [Apple's API documentation](https://developer.apple.com/documentation/servicemanagement/smappservice) confirms macOS 13 availability. The pinned `tauri-utils` 2.10.2 `config.rs:694` returns the default `10.13`; `objc2` 0.6.5 `src/__macro_helpers/cache.rs:84` panics when a class is unavailable. The adapter has no availability check.

**Suggested fix:** guard both adapter operations inside `platform` and return `Unsupported` before touching `SMAppService` on older systems, so ordinary settings still work. Alternatively, obtain agreement to require macOS 13 and set the bundle/deployment minimum explicitly. Test the unsupported availability path without invoking the class.

### R4 — Minor: oversized legacy daily logs survive the new directory budget

**Location:** `src-tauri/src/logging/rotation.rs:118`; migration at line 57.

Pruning limits file count but preserves oversized daily files written by the previous logger. An upgrade can retain four large legacy files alongside the new active file, exceeding the documented 10 MiB budget until subsequent rotations age them out.

**Evidence:** the same standalone rotation harness seeds five 1,000-byte legacy daily files, then opens with `max_bytes=100, keep=5`. The resulting directory still holds 4,000 bytes against its declared 500-byte budget.

**Suggested fix:** enforce the byte budget on legacy files during startup migration, preserving unrelated files. Follow-up: [tech-debt #106](https://github.com/gargankit90/dictation-app/issues/106). This minor does not independently block approval.
