## Findings

### B1 — Blocker: the overlay can invoke every custom app command

**Location:** `src-tauri/capabilities/overlay.json:6`; related: `src-tauri/build.rs:2`, `src-tauri/src/lib.rs:169`, `src/overlay/capability.test.ts:61`.

The two event permissions restrict Tauri plugin commands, but do not restrict the application's registered commands. This branch uses plain `tauri_build::build()` and tracks no application permission manifest. Tauri 2.12.5 therefore bypasses ACL rejection for local custom commands (`tauri/src/webview/mod.rs:2078–2084`). The newly created overlay can invoke `get_settings`, `save_settings`, `set_api_key`, `has_api_key`, and `test_api_key`: it can change settings, overwrite a stored key, or initiate a provider key check. That violates criterion 2 and the per-window least-privilege requirement. Scanning imports and the capability JSON cannot establish command isolation.

**Reproduction:** `/tmp/m51-review-probe/src/main.rs`, run with `CARGO_TARGET_DIR="$PWD/target" cargo run --manifest-path /tmp/m51-review-probe/Cargo.toml`. It uses Tauri's headless MockRuntime, the actual overlay capability and core permission manifests, and a harmless custom command named `save_settings` returning a sentinel. No native windows, keychain access, network requests, VM, or screen interaction occur. The overlay request prints `has_app_acl=false: Ok(Json("\"CUSTOM COMMAND EXECUTED\""))`; enabling the app ACL with no custom command grant changes the result to `Err`. Output: `/tmp/m51-review-probe.log`.

The worktree already contained untracked `src-tauri/permissions/` from an earlier checkout. Those files can accidentally enable app ACL checks locally, masking the clean-checkout failure; they are not part of this PR and were left untouched. The probe explicitly excludes that stale generated app manifest.

**Suggested fix:** declare all custom commands through `tauri_build::AppManifest::commands`, grant them only to `main`, and test actual invocation denial from `overlay`. #95 supplies the related app-command hardening; incorporate that change or land/rebase it first, then update its capability tests for the overlay's two event commands. Approval must cover the resulting merged ACL, rather than relying on the future merge to fix isolation. [Tauri's documented custom-command default](https://v2.tauri.app/security/capabilities/) confirms this behavior.

### M1 — Major: creation immediately converts the NSPanel back to a TaoWindow

**Location:** `crates/platform/src/overlay/macos.rs:75`.

`Panel::to_window()` is a conversion operation, not an accessor. In the pinned `tauri-nspanel` 2.1.1 implementation (`src/panel.rs:359–390`), it removes the panel from the plugin registry, clears its event handler, and calls `object_setClass` with the saved original class before returning the Tauri window. Thus every successful `Window::create` immediately undoes `PanelBuilder`'s conversion: the resulting native object is a regular `TaoWindow`, not `OverlayPanel`/`NSPanel`. The custom panel overrides and NSPanel-specific non-activation behavior are no longer installed. Retaining `PanelHandle` does not undo this class restoration.

The separate `focusable(false)` setting and `orderFrontRegardless` still reduce focus risk; this finding does **not** claim that the current TextEdit test demonstrates a focus theft. The concrete failure is that the required non-activating NSPanel is dismantled on every creation. This also explains why checking layer 25, size, frontmost app and paste destination can pass without proving that a panel survived initialization.

**Suggested fix:** retrieve the existing webview window through `tauri::Manager::get_webview_window(spec.label)` without calling `to_window()`, or retain it during construction. Keep the actual panel registered and retain the present main-thread show/hide dispatch. Add a VM/native regression check that the created window remains an NSPanel (and cannot become key/main) after initialization. Evidence is direct inspection of the exact pinned dependency; no native-window reproduction was attempted under the no-screen/no-VM constraint. The dependency explicitly documents `to_window` as converting back to a regular window (`src/lib.rs:87–90`).
