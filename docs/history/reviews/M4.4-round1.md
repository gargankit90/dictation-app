## Findings

### R1 — Blocker: shell tracing exposes the real API key

Location: `tests/e2e/scenarios/e2e_real_groq.sh:16` and `:27`;
`tests/e2e/scenarios/_groq_helpers.sh:18` and `:23`.

Running the scenario with `bash -x` prints the expanded key to stderr. The
initial presence check, the `groq_key_store` call, its local assignment and
the `printf` command all expose it; `groq_log_lacks_key` also expands it under
tracing. Using stdin for `security -i` protects process arguments, but does
not protect the host's shell trace. A captured diagnostic run or CI trace
therefore contains the credential even when the app log passes its check.

Reproduced outside the repo with an explicitly fake sentinel and a stubbed
`vm` that only consumes stdin. No keychain or network access was involved:

```bash
source tests/e2e/scenarios/_groq_helpers.sh
vm() { cat >/dev/null; }
set -x
groq_key_store gsk_REVIEW_SENTINEL_NOT_REAL
```

The standalone reproducer is `/tmp/m44-review-repro.sh`; its run produced
four occurrences of the sentinel in
`/tmp/m44-review-repro.alpTZ2/trace.stderr`. Only fake credentials were used.

Suggested fix: disable or reject xtrace at the runner's entry before any
secret expansion, including the scenario's presence check and helper calls.
Disabling it inside `groq_key_store` is too late because the caller's
arguments have already been traced. Keep tracing disabled through the log
leak check as well. Add a fake-key regression that runs the entry point with
tracing enabled and verifies that neither output stream contains the key.

### R2 — Major: failures after key storage leave the key in the VM

Location: `tests/e2e/scenarios/e2e_real_groq.sh:27`–`:36` and
`tests/e2e/scenarios/_groq_helpers.sh:31`–`:32`.

Deletion happens only after `groq_dictate` returns. With the runner's
`set -e`, a failed launch/SSH command on line 28, or the unguarded TextEdit
setup on line 32, exits before deletion. There is no EXIT/signal cleanup.
The VM is not destroyed when the runner exits, so the credential remains in
its login keychain, with the helper's `-A` access policy, beyond this run.
Also, `groq_key_remove` suppresses every deletion error with `; true`, so a
locked keychain or other deletion failure can leave the key behind even on
the normal path without failing the run.

Reproduced in `/tmp/m44-review-repro.sh` by sourcing the actual scenario and
helper, substituting an in-memory-equivalent marker file for keychain
storage, and making `launch` return 23. The scenario exited 23 and the
marker remained; the deletion stub was never called. This exercises the
actual control flow without a VM, real key, or owner-screen interaction.

Suggested fix: install cleanup before attempting storage, run it on normal
exit and failure/signals, and preserve the original scenario status. Treat
an absent item as success but report other deletion failures; if SSH is
unavailable, report that cleanup could not be verified rather than silently
claiming removal. Apply the same cleanup discipline to the bad-key scenario.
Add regressions for launch/TextEdit failure and deletion failure.

## What I checked

- Read the full PR diff, milestone, engineering rules, reviewer role and
  every checklist section. PR notes disclose the unrun VM scenarios and
  identify the Lead's authorization for the e2e changes.
- Traced startup and both save commands through `changed`, `LiveEngine`,
  `Transcribers` and `OpenAiCompat`. The update mutex serializes builds;
  transcription snapshots an `Arc<Engine>` before awaiting, so a save does
  not cancel, duplicate or replace an in-flight request. The next call uses
  the updated engine. Saves and rebuilds run on the blocking pool.
- Keys come from `SecretStore` in Rust. Engine and secret Debug output is
  redacted; Authorization is marked sensitive; provider error bodies are
  discarded; redirects are disabled. No new IPC returns a key. The active
  engine retains its key until replacement/shutdown; an old engine remains
  alive while its in-flight request finishes. External keychain changes
  require a save or restart, as disclosed in the PR notes.
- Checked all `TranscribeError` user-message branches and the pipeline's
  error-to-Idle path. Missing key sends no request; failed transcription
  never reaches insertion. Wiremock and in-memory store tests cover wrong
  keys, retries, provider changes, missing/unreadable settings and recovery.
- Forwarded launches parse flags but only warn about `--transcriber`;
  engine choice is applied solely during initial setup. This path does not
  let a second launch switch the engine, including in release builds.
- Examined script quoting and stdin transport: the normal SSH/security
  argument vectors do not contain the key, and no temporary key file is
  created by the new helpers. The failures above concern shell tracing and
  credential cleanup.
