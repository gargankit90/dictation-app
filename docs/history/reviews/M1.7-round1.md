## Findings by severity

### Major R1 — A cold-start forward can be acknowledged before its debug event has anywhere to go

**Location:** `src-tauri/src/lib.rs:167` (listener starts), `src-tauri/src/lib.rs:175` (callback returns regardless of injection), `src-tauri/src/lib.rs:265` (pipeline starts later), and `src-tauri/src/lib.rs:306` (failed injection is only logged). [Inline comment](https://github.com/gargankit90/dictation-app/pull/95#discussion_r4434416608).

The first instance acquires and binds, constructs `SyntheticHotkey`, and immediately starts the forwarding callback, before Tauri is built or its `setup` callback runs. The synthetic sink is initially absent. During that interval, a second launch with `--press` is parsed and `Injector::inject` returns `false` (`crates/app/src/test_hooks.rs:172`). `handle_flags` returns normally, `serve` sends ACK, and the secondary exits successfully. Starting the pipeline afterward does not recover the lost event. This is a concrete hidden-delivery failure during the cold-launch scenario this milestone hardens; it affects debug test hooks, not release recording permissions.

**External reproduction:** `/tmp/m17-review-harness/tests/edge_cases.rs`, test `startup_ack_can_precede_hotkey_start_and_lose_press`. It includes the production platform module and shell parser by absolute path and uses the actual pipeline `SyntheticHotkey` with an inert OS source. It drives the same order as `run`: acquire, construct hotkey/injector, listen with parse/inject callback, forward `--press`, then start the hotkey. The first acquire returns `Forwarded`, the callback records `inject=false`, and the eventual sink has received **0 events**. A subsequent `--release` after start is ACKed and delivered, demonstrating the startup interval rather than a broken harness sink. No GUI, real keyboard hook, microphone, or owner-screen access is involved.

```text
STARTUP: secondary returned Forwarded/exit-0; inject=false; 0 events after hotkey.start
```

**Suggested fix:** keep lock acquisition and binding before Tauri construction, but consume/ACK forwarded messages only after the pipeline and initial-launch configuration are ready. Alternatively queue them until readiness with an explicit bounded/failable delivery policy. Add a regression that holds startup before `Pipeline::spawn`, forwards an event, then completes startup and proves that success means the event was retained and delivered. The current platform race tests use an immediately ready channel callback and cannot detect this shell integration gap.

### Minor R2 — Existing directories and symlink entries are trusted without validating the documented privacy guarantee

**Location:** `crates/platform/src/single_instance/mod.rs:206`–`211` (existing directory) and `crates/platform/src/single_instance/mod.rs:181` (lock open). [Inline comment](https://github.com/gargankit90/dictation-app/pull/95#discussion_r4434416660). Follow-up: [tech-debt #96](https://github.com/gargankit90/dictation-app/issues/96).

`DirBuilder::mode(0700)` applies only to new directories. External tests `existing_directory_permissions_are_not_validated` and `symlink_directory_and_lock_are_followed` show that acquire succeeds in an existing **0777** directory without changing its mode and follows both a directory symlink and a lock-file symlink. The lock target is not truncated. The claim that the resulting directory can only be entered by this user is therefore a precondition for existing paths, rather than something the function enforces.

This is nonblocking hardening for the present macOS app: its normal cache/per-user temporary paths have a user-controlled parent, and this review did not demonstrate another-user exploit of those defaults. Same-UID processes already have access to the application and can replace the lock inode; this is not a claim that this module should isolate hostile processes sharing a UID. An existing shared `Config::in_dir` path, or a future Linux fallback into shared `/tmp`, needs the stronger check.

**Suggested fix:** document the trusted-directory precondition or validate existing directory ownership/type/private permissions and reject untrusted symlink entries; fail closed for an untrusted directory. Add existing-mode and symlink regressions. Do not promise isolation from same-UID processes.

## Correctness and threat-model checks

- **Lock/bind ordering and stale-socket race:** one opened lock inode is held across stale unlink, bind, listener lifetime, and socket removal. A competing well-behaved launch cannot unlink or bind while that lock is held. Bind failure returns an error, dropping the lock; a lock holder that binds late is retried. `Instance::drop` stops acceptance and unlinks before unlocking. The old loser cleanup no longer exists. This protection assumes the directory/lock inode is not externally replaced; see R2 for existing-directory trust.
- **Other users versus same user:** new directories are 0700; the socket and lock inherit ordinary file modes inside that directory. The directory is the access boundary. A protected cache parent prevents another UID planting a stale socket or symlink there. Same-UID processes can connect by design, can replace filesystem entries, and are not isolated by flock; no stronger guarantee is claimed here. No cross-user test was performed with another account.
- **Frames and partial reads:** body lengths above 64 KiB are rejected before receiver allocation. Counts are checked against the minimum bytes remaining before reserving strings; lengths use checked splitting; bad UTF-8, truncated count/string fields, and extra bytes in the announced body are rejected. The read loop handles short reads/interruptions and recomputes the remaining total deadline, so trickling cannot renew it indefinitely. Tests cover maximum body, oversized prefix, huge count, malformed UTF-8 and trickle timeout. No new unsafe code was introduced.
- **Reader/concurrency cap:** the accept loop reserves at most eight RAII reader slots. Excess connections close unread and secondary processes retry. Slots release even on panic or reader-thread spawn failure. A finite burst of idle peers ages out at the I/O deadline; an actively replenished same-user flood has no fairness guarantee. The mutex serializes callbacks; the read deadline does not cancel a callback or bound time waiting for that mutex. The shell callback is finite parsing/logging/injection; no additional concrete hung-callback defect was established.
- **ACK semantics:** ACK means the callback returned, not that recording/transcription completed. Timeout can leave delivery uncertain, so refusing automatic retry after ACK timeout avoids duplicating a potentially handled message. An unresponsive owner makes a secondary exit 1 while retaining the singleton lock: that is an acceptable explicit failure and avoids creating a second microphone/pipeline owner. There is no automatic hung-owner recovery. R1 is different: the callback already knows injection failed, but the launch still gets success.
- **Forwarded flags:** both initial and forwarded paths use `flags::TEST_FLAGS = cfg!(debug_assertions)`. Release hotkey construction has no injector; release parsing ignores press/release and debug audio flags. Forwarded audio/transcriber choices do not reconfigure the running pipeline. The 11 production parser tests pass in an actual optimized release build. Existing argument-consumption/duplicate-warning issues #73/#70 are not re-raised.
- **Capabilities and Settings:** app manifest generation activates ACL checking for custom commands; capability JSON grants exactly five app permissions and no core permissions. Window show/unminimize/focus and close-to-hide are Rust calls (`src-tauri/src/lib.rs:187`, `:334`), so they do not need frontend window permissions. Current UI calls only the five typed bindings; Vitest passes **57/57**. CSP and remote-origin restrictions are unchanged. Native Settings interaction remains a Tester/Lead VM check; this review makes no GUI-pass claim.
