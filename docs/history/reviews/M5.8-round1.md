## Password-field decision

`crates/platform/src/cursor/macos.rs:310` preserves the AX error until the
subrole decision, rejects a non-string result, and propagates timeout,
permission, invalid-element and other failures. `read_field` at line 374
checks the subrole before requesting either the cursor or text. The recording
fake checks that a secure or unreadable subrole causes exactly one request,
`AXSubrole`; no cursor or `AXStringForRange` request follows.

The absent-subrole exception at line 230 is reasonable for the AX contract:
`AttributeUnsupported` means that this element does not support the attribute;
`NoValue` means the attribute has no value. These are distinct from a messaging
failure. The SDK's `AXAttributeConstants.h` documents subrole as optional unless
needed to describe the element's semantics, and `AXRoleConstants.h` defines
`AXSecureTextField` as the secure-field subrole. Treating every missing subrole
as an unreadable field would discard ordinary text context, including the
plain-field control covered here. The implementation compares the secure
subrole exactly, including its full UTF-16 contents.

This is an AX-based guarantee: Secure Input and correctly reported secure
subroles prevent reads, and communication/type failures fail closed. It cannot
identify a custom password widget that neither enables Secure Input nor reports
its secure semantics. I found no concrete supported-widget leak from the
absent-subrole distinction and am not treating hypothetical AX misreporting as
a blocker. The PR explicitly records this limitation.

Primary references: [Apple's attribute-copy return codes](https://developer.apple.com/documentation/applicationservices/1462085-axuielementcopyattributevalue)
and [secure text field subrole](https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/subrole/securetextfield).
The matching local SDK headers were also inspected.
