## Findings

### R1 — major: a failed launch leaves Right Option held

Location: `tests/e2e/scenarios/e2e_held_at_launch.sh:9` (down at line 8),
with `tests/e2e/run.sh:76` and `tests/e2e/lib_full.sh:103`.

After posting Right Option down, the scenario calls `launch_full` outside
`expect`. If that SSH/open command fails, `set -e` exits the runner before
the up event at line 19. There is no EXIT/INT/TERM trap. This leaves the
VM's global Right Option state down; Terminal jobs, the app and documents
can also survive an early exit. The successful-path `close_terminal` and
the runner's final `fresh_app_state` do not run. Likewise, a timed-out
Terminal job is not cancelled and can keep posting events after the caller
has proceeded. This prevents reliable unattended recovery/reuse with
`--no-reset` and can contaminate later hotkey tests.

Reproduction without the VM: `/tmp/m43-shell-review.sh` sources the actual
helpers/scenario, replaces environmental boundaries with fakes, records
`real_key` events to a file, and makes `launch_full` return 73. The scenario
exits 73 with `key_state=down`; no release or cleanup occurs. No VM or host
GUI was accessed.

Suggested fix: register failure/signal cleanup before posting any down
event. Best-effort release Right Option, cancel/reap outstanding Terminal
jobs, close scenario-owned documents/windows, and stop the app while
preserving the original exit status and collecting available diagnostics.
Give the generated hold script its own exit/signal release trap, and
cancel a job when `vm_terminal` times out. Verify with an injected failure
immediately after down and an interrupted/timed-out hold.

### R2 — major: the rapid scenario does not verify paste order

Location: `tests/e2e/scenarios/e2e_rapid.sh:25` and `:28`.

Acceptance criterion 4 explicitly requires five pastes **in order**. All
five replies are `hello world`, and the checks only count that substring,
remove it, and compare phase names. A regression that moves the insertion
point to the beginning before every paste produces the reverse order of
dictations, but exactly the same document and state log, so every check
still passes. Repeating identical phase names does not establish which
dictation's text was inserted. Replaying the first result for later jobs
would also be indistinguishable.

The environmental-fake run in `/tmp/m43-shell-review.sh` invokes the actual
scenario with the observable result of that prepend regression. All
checks PASS and `SCENARIO_FAILED=0`. This is a missing assertion for a
numbered acceptance criterion, rather than a demonstrated production
ordering bug.

Suggested fix: use distinct per-dictation mock responses and compare the
entire expected document in chronological order. Alternatively, put
distinct boundary markers in TextEdit between cycles and assert the exact
accumulated document after each cycle, so a prepend or misplaced paste is
observable. Demonstrate that a prepend/reorder mutation fails the test.

## Scenario mutation reasoning

| Scenario | Plausible regression the assertions catch | Limits |
| --- | --- | --- |
| `e2e_startup` | Second instance fails to forward Pressed, or initializes a second app | Primarily shell lifecycle/log assertions |
| `e2e_press_release` | Release is lost, file audio does not reach insertion, or transcript leaks into the log | Does not independently read the target document |
| `e2e_real_mic` | Missing mic grant, failed capture, empty/too-short capture, or failure to return Idle | Allows silent capture only with `verdict=Silent`; cannot prove audible speech quality or distinguish a zero-filling capture adapter from genuine silent input |
| `e2e_mock_paste` | Mock flag ignored, paste lost/wrong target, or transcript logged | Exact TextEdit readback verifies actual paste |
| `e2e_clipboard_restore` | Inserter leaves its transcript on the clipboard instead of restoring the sentinel | First paste is read back; second cycle principally checks restoration |
| `e2e_silence` | Assessment removed or wrong threshold causes the known mock text to be pasted for zeros | Also requires the Silent verdict, no Inserting phase and unchanged clipboard |
| `e2e_rapid` | Dropped or duplicate cycle, stuck busy state, extra text or missing paste | Cannot catch reordered/misplaced pastes: R2 |
| `e2e_hold_release` | Real Right Option down/up no longer reaches the hotkey matcher, or release fails to stop capture | Uses actual posted flagsChanged events; no synthetic flag fallback |
| `e2e_held_at_launch` | Release of the already-held key is interpreted as a press and starts recording, or the next normal hold fails | Not run against a pre-M1.6 binary; failure cleanup is R1 |

## M4.2 integration

`origin/main` advanced to merge #94 (`8149fac`) during this review; the
reviewed branch still predates it. On this head rejected audio deliberately
returns an empty string and shows `EmptyTranscript`. M4.2's
`cleaned_event` maps an empty successful transcript to `TranscriptDropped`,
which returns Idle without an error. Preserve that behavior when
integrating main, and update the new pipeline assertions that currently
expect `UiEvent::Error(EmptyTranscript)`; do not reinstate an error merely
to satisfy the older expectations. The silence e2e phase expectation
remains compatible. The changed transcriber result type also needs the
normal integration adaptation. This is a known branch-integration task,
not an additional finding against the reviewed snapshot.
