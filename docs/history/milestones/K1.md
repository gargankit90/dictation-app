# K1: record the dictation key by pressing it (closes #170)

Acceptance criteria:

1. [auto] Settings → Dictation key shows the current key as a keycap (e.g.
   "Right ⌥", "Right ⌘", "⌃⇧Space"), with "Record a different key". While
   recording, the next key or combination the user presses becomes the new
   key; sided modifiers are distinguished (Right ⌘ vs Left ⌘); a modifier
   pressed and released alone records that modifier (e.g. Right ⌘ →
   RightCmd); Esc cancels; "Reset to default" restores Right Option. Stored
   as the existing hotkey_spec text (no format change, no migration).
2. [auto] Keys that can't work are refused with a plain reason: plain
   letters/digits without a modifier, Esc, keys the platform adapter can't
   register. Conflicts the app can detect (e.g. registration fails) show a
   message and keep the old key.
3. [auto] The new key works immediately (no relaunch) and after relaunch;
   tests at the spec/adapter level and vitest for the recorder UI
   (recording, cancel, reset, refusal).
4. [auto] Onboarding: the existing key step (if present) uses the same
   recorder component; otherwise add a minimal "Your dictation key"
   confirmation on the try-it step showing the keycap and the same recorder.
   Keep the rest of onboarding unchanged (the redesign is #210).
5. [auto] Recording the key needs key events while the Settings window is
   focused; it must not require extra macOS permissions beyond today's.
6. [manual] In a VM via tests/e2e/run.sh locks: record Right ⌘ in Settings,
   dictate with it, relaunch, dictate again. If an e2e scenario is practical
   (set the key via the recorder with a scripted key press from the
   Terminal.app helper used for key holds), add it.

Out of scope: tap-vs-hold modes, multiple keys, a cancel key.
