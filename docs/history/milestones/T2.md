# T2: real app journeys — hotkey setting, Settings, launches, VM helpers

## Goal

Catch the bugs a user would hit in the real app, not just in unit tests: a
hotkey change in Settings that doesn't take effect, a Settings save that half
works, launching the app twice at once, and VM tests that report success when
the app failed. From the test audit, #103 (T2 in its milestone split),
without the CI runner work (P1-06, owner decision #104).

## Scope

- **P1-03 — saved hotkey actually controls dictation.** Today the shell builds
  the hotkey from the default and the Settings save rebuilds only the
  transcriber. Apply the saved hotkey at startup and when Settings is saved
  (re-register the listener; on failure keep the old one and show a clear
  error; "Settings saved." must not claim a change that didn't apply).
  Extract the policy into `crates/app` so it's testable with an injected
  hotkey factory.
- **P1-01 — single-instance under real launches.** Process-level tests on the
  current `dictation_platform::single_instance` (M1.7/M1.7.1): concurrent cold
  starts give one owner; a losing contender can't unlink the owner's socket;
  an idle or oversized peer can't starve a real launch; a malformed frame then
  a valid frame recovers; a forwarded launch needs its delivery ack. Add
  `e2e_single_instance_cold_race` (several launches without waiting for ready:
  one tray/pipeline; a later launch still forwards).
- **P2-01 — Settings and permissions in the real app.**
  `main_capability_denies_native_tray_and_menu_mutation` using Tauri's real
  ACL resolution (main's needed commands allowed; tray/menu/resource mutation
  and remote origins denied). Settings edge tests in `src/Settings.test.tsx`:
  partial save keeps the saved key status and allows retry; a failed re-read
  doesn't claim unsaved values; a late Test-key result is ignored; Enter while
  busy starts no second save. VM `e2e_settings_save_reopen` (open Settings
  from the tray, change and save, close and reopen: values persist; the
  hotkey change from P1-03 works right away and after relaunch) and
  `e2e_tray_error_clears_on_next_recording`.
- **P2-04 (build only):** `npm run build` (the production frontend) on every
  PR in CI; keep the gate under ~10 minutes.
- **P2-05 — VM helpers can't hide failures.** `vm_terminal` and friends
  propagate the guest's exit status and deadlines; stale done files are
  rejected; cleanup doesn't mask a failed Quit; stubbed
  `tests/e2e/test-runner.sh` cases prove a guest failure turns the scenario
  red. Then three user scenarios: `e2e_secure_input_blocks_paste`,
  `e2e_user_copy_wins`, `e2e_quit_during_recording_then_relaunch`.

## Out of scope

- VM e2e in CI (owner decision #104). Overlay channel bound (#112) and the
  overlay ACL test extension (#110) wait for M5.1 (#102) to merge; include
  them only if #102 is on main by the time you get to them.

## Acceptance criteria

1. `[auto]` The saved hotkey is the one listening at startup and after a
   Settings save; a failed re-registration keeps the old hotkey and shows an
   error; tests with an injected hotkey factory prove all three.
2. `[auto]` The single-instance process tests in Scope pass 50 runs in a row
   under CPU load; `e2e_single_instance_cold_race` passes in the VM.
3. `[auto]` The main-window ACL test passes and fails if a tray/menu mutation
   permission or a remote origin is added.
4. `[auto]` The four Settings edge tests pass and fail against the bug they
   describe.
5. `[auto]` `npm run build` runs in CI on every PR.
6. `[auto]` A stubbed guest failure (nonzero exit, timeout, stale done file)
   makes the scenario fail; the existing 39 key-handling checks still pass.
7. `[auto]` The new VM scenarios pass in a full `tests/e2e/run.sh`:
   `e2e_settings_save_reopen`, `e2e_tray_error_clears_on_next_recording`,
   `e2e_single_instance_cold_race`, `e2e_secure_input_blocks_paste`,
   `e2e_user_copy_wins`, `e2e_quit_during_recording_then_relaunch`.
8. `[manual]` On the owner's Mac: change the hotkey in Settings, save, and
   dictate with the new hotkey without restarting; then relaunch and it still
   works.

Every milestone also needs: the gate green, coverage at or above thresholds,
`Tester: PASS` and `Reviewer: APPROVED` on the PR.
