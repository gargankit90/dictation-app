# E1: Easy error diagnosis for users

Part of #209. Owner: "I want an easy way to diagnose errors for users." When
something goes wrong, the user can fix it themselves or produce a useful
report in two clicks, without anything private leaving the Mac unless they
choose to share it.

## Acceptance criteria

1. [auto] Every user-facing error has a stable error code (enum, e.g.
   `mic_denied`, `accessibility_missing`, `key_rejected`, `key_unreadable`,
   `network_unreachable`, `provider_quota`, `model_missing`,
   `model_loading_failed`, `paste_failed`, `hotkey_unregistered`) and a plain
   next step shown with it (overlay/tray/onboarding), e.g. "Microphone is off
   for the app → Open Microphone Settings". One table maps code → message →
   action; tests cover every code. Reuse A1's `error_type` where it exists
   rather than adding a second taxonomy.
2. [auto] Troubleshoot window (tray menu "Troubleshoot…", and Settings): live
   checks with ✓/✗ and a fix action each: microphone permission,
   Accessibility, hotkey registered, engine ready (local model present and
   loadable / cloud key readable), provider reachable (cloud only, only when
   the user presses "Test connection"), last error code and when. Checks run
   off the event loop; nothing records audio unless the user presses a mic
   test button.
3. [auto] Report a problem: builds a diagnostics report ONLY from allowlisted
   structured fields: app version, macOS version, arch, permission states,
   hotkey, engine kind + model id or provider, readiness, last N error codes
   with timestamps, analytics on/off. Never audio, transcripts, typed or
   clipboard text, API keys, app names/window titles, file paths, usernames,
   raw log lines, provider response bodies. Shows the exact text before
   anything happens; actions: Save report… (file), Copy, and "Open a GitHub
   issue" (opens the browser with a prefilled issue whose body is the report;
   the user submits it themselves). Nothing is uploaded by the app.
4. [auto] A test plants secrets and text in every input that could reach the
   report (key, transcript, clipboard, app name, home path) and asserts none
   appear in the report. Mutation-check it yourself (add a raw log line to the
   report, the test must fail).
5. [auto] Errors that already reach analytics/Sentry stay governed by the
   analytics switch; the report is separate and never sent automatically (doc
   in `docs/privacy.md`).
6. [auto] Gate passes; vitest for the Troubleshoot and Report UI.
7. [manual] In the VM: deny the microphone, see the error with its next step;
   open Troubleshoot, see ✗ microphone with a working fix button; produce a
   report and check its contents.

Out of scope: Sentry crash reporting (A2), onboarding redesign (#210), a log
viewer.
