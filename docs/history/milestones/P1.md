# P1: the first dictation after launch is pasted (closes #239; part of #203 until confirmed)

Users can lose their first dictation after launching the app: it is recorded
and transcribed, but the text isn't pasted. That's the worst first impression
for a dictation app.

Acceptance criteria:

1. [auto] Reproduce reliably first: in a VM via `tests/e2e/run.sh` locks
   (`E2E_VM=dictation-vm-2` or `dictation-vm`), a scenario that relaunches the
   app and immediately dictates once (both with the default Right Option and
   with a combination such as Ctrl+Shift+A), repeated in a loop (e.g. 10
   relaunches), and records whether each first paste landed. Report the
   failure rate before the fix.
2. [auto] Root cause, stated plainly in the PR with evidence from logs:
   candidates include the combination's modifiers still held when the
   synthetic Cmd-V is posted (so the target sees Cmd+Ctrl+Shift+V), the event
   source/tap not being ready right after launch, the clipboard being restored
   before the target reads it, focus not yet returned to the target app after
   the overlay appears, or Accessibility trust not effective for the first
   post. Check which it is; don't guess.
3. [auto] Fix it in the product (not only the test), with a unit test where
   the logic allows (e.g. paste waits for all hotkey modifiers to be released,
   or the restore waits until the target read the clipboard), and the VM loop
   from criterion 1 shows 10/10 first pastes landing for both keys.
4. [auto] If a paste still can't be confirmed, the user isn't left with
   nothing: the transcript stays on the clipboard (or the existing E1
   paste_failed path shows it with Copy), never silently lost. Test it.
5. [auto] Add the relaunch-and-dictate loop as a VM scenario (shorter, e.g. 3
   relaunches per key) so it runs in every post-merge suite.
6. [auto] Gate passes; hosted CI green.
