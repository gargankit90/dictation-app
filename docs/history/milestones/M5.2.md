# M5.2: onboarding

## Goal

Walk a first-time tester from install to a working dictation, without a
relaunch they don't understand.

## Scope

- Steps: Microphone permission → Accessibility permission → provider and key
  (with Test) → try a test dictation.
- Each step moves on only when its condition is met; the window shows on
  first launch (no key saved, or a permission missing) and can be reopened
  from the tray.
- **#50 Accessibility re-grant.** Find out on macOS 13+ whether a running
  app picks up a newly granted Accessibility permission (`AXIsProcessTrusted`
  polling plus M5.5b's hotkey supervisor, merged as `m5.5b`). If it does,
  the Accessibility step advances by itself; if not, the step says
  "Relaunch to finish" with a Relaunch button that restarts the app and
  reopens onboarding at the same step. Write down the answer in
  `docs/ENGINEERING.md`.
- Privacy: the key goes only to the keychain, as in Settings; the test
  dictation's transcript is shown in onboarding and never logged.

## Out of scope

- Account systems of any kind. Windows.

## Acceptance criteria

1. `[auto]` Vitest: each step advances only when its condition is met
   (mockIPC); going back and reopening from the tray resume at the right
   step; a failed key Test keeps the user on that step with the error.
2. `[auto]` Rust tests for the onboarding commands (permission status, step
   state) with fakes.
3. `[auto]` A VM scenario `e2e_onboarding_first_run` on `dictation-vm`: with
   no saved key, onboarding shows at launch, the key step accepts a made-up
   key against T4a's local provider (if #157 is merged; otherwise the mock
   engine), and the test dictation pastes into the onboarding field.
4. `[manual]` In a freshly restored VM, onboarding takes a new user to a
   working dictation (the owner, or the Tester on `dictation-vm-2`).

Every milestone also needs: the gate green, coverage at or above thresholds,
`Tester: PASS` and `Reviewer: APPROVED` on the PR.
