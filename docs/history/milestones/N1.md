# N1: release signing ready for Developer ID and notarization (#206)

The owner paid for the Apple Developer Program on 2026-11-06, and Apple is
processing the order. This milestone gets everything ready before the
certificate exists. Credentials stay on the owner's side, in the Keychain:
agents never read the update key, the Keychain items or an Apple credential,
and never run `scripts/release.sh --publish`. The owner runs the real signing
and notarization steps.

## Acceptance criteria

1. [auto] Hardened runtime on every release build, with the fewest
   entitlements that work: microphone for certain, and anything else only if
   it's shown to be needed. Write down why each one is there. Find out what
   WKWebView, transcribe.cpp and the bundled native libraries need. Don't add a
   broad entitlement such as disable-library-validation or
   allow-unsigned-executable-memory unless a test fails without it.
2. [auto] It works under hardened runtime. Test in the VM with a hardened build,
   using the self-signed dev certificate: mic capture, real hotkey, paste, the
   local model (load and transcribe), Keychain read, overlay, launch at login,
   and update. Run the full VM suite against a hardened build, and report
   anything that differs from a normal build.
3. [auto] `scripts/release.sh` picks its identity from configuration: Developer
   ID when set up, with today's dev certificate still working as the fallback
   until then. It fails with a clear message when notarization is requested but
   its credential is missing. It never prints a credential.
4. [auto] Notarize and staple the DMG and the app in the release flow, and
   verify the result in the script (`spctl`, `stapler validate`). The
   notarization parts can't run yet, so test the logic with a fake notary tool,
   and say plainly what stayed untested. Check that the updater bundle is signed
   by the same identity and still passes the minisign check.
5. [auto] Moving from the dev-signed build to a differently signed build: test
   it in the VM with a second self-signed certificate standing in for Developer
   ID. An update installs, the app detects its lost permissions, tells the
   person plainly and recovers without reinstalling, and settings, history and
   the saved key survive (a Keychain prompt is fine). Say what real Developer ID
   may do differently.
6. [manual] Owner steps in `docs/releasing.md`, written for someone doing this
   for the first time: create the Developer ID Application certificate, set up
   the notarization credential so the key stays on their side, do a test signing
   run, verify, and what to do when the certificate expires. Include how to
   confirm #259 (no Keychain prompt on update) once the real certificate exists.
7. [auto] `docs/TESTERS.md` has both versions of first launch ready: the current
   quarantine steps, and the simpler one for notarized builds, marked as to be
   switched at the first notarized release. Don't remove the current steps yet.

## Out of scope

The real certificate and credential, publishing, and any change to the updater
key.
