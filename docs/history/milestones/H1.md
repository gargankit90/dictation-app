# H1: long dictations must not fail on a slow connection

Owner-approved fix before 0.1.0.

## Problem

`DEFAULT_TIMEOUT` is 30 s for the whole request
(`crates/transcribe/src/openai_compat.rs`, applied in
`crates/transcribe/src/http.rs`), with 3 attempts (`crates/core/src/retry.rs`).
A recording can run 5 minutes (`crates/core/src/coordinator.rs`), about 9.6 MB
of WAV, which needs about 2.6 Mbps upstream to finish in 30 s. Below that, a
long dictation fails all 3 attempts and the audio is gone. FreeFlow has the
same bug (its issue #331). Found by reading the code; reproduce it first with
a local slow server.

## Acceptance criteria

1. [auto] A request's timeout grows with the clip: 30 s plus 0.5 s for each
   second of audio. A 5-minute clip gets 180 s. Clips under about 10 s stay
   close to today's limit. It is set per request, not by rebuilding the
   client. The calculation is pure code in `crates/core` with a unit test.
2. [auto] A dead network still fails fast at any clip length: a connect
   timeout of about 10 s. The PR says what was chosen and why.
3. [auto] When a clip of 60 s or more times out, retry at most once. Other
   failures keep the current policy, as does everything shorter than 60 s.
4. [auto] A test against a local slow server shows that a clip which needs
   longer than 30 s to upload now succeeds, and that a server which never
   responds fails with today's timeout error, within the new limit.
5. [auto] Esc during that longer wait still cancels straight away and pastes
   nothing. Check whether `e2e_cancel_and_busy_presses` already proves this;
   extend it if not.
6. [auto] Key check, model downloads and local models behave as before.
   Model downloads have their own client.

## Out of scope

Keeping the audio after a failure, compressing audio, any UI change.

## Recorded exception to the layout rule

`crates/transcribe/src/http.rs` has one `#[cfg(any(target_os = "linux",
target_os = "android"))]` call, `tcp_user_timeout(None)`. reqwest 0.13 sets
`TCP_USER_TIMEOUT` to 30 s by default on those targets, which kills a
stalled upload at 30 s whatever the per-request limit. The reqwest method
exists only on those targets, so it can't be called without a cfg. The Lead
decided on this narrow exception to "`#[cfg(target_os)]` only in `platform`"
over moving it into `platform` (which would break the dependency direction)
or skipping the test on Linux. Vocet ships only on Mac today, so it has no
user impact now; Linux would need it if it ever ships.
