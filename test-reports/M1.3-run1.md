## Untested behaviour found

New tests in `crates/app/tests/pipeline_edges.rs`. A gated transcriber holds a dictation in Transcribing until the test opens the gate; time comes from `FakeClock`, with no sleeps; `settle()` yields on the current-thread runtime so the pipeline task drains its queue.

- `a_press_while_transcribing_is_ignored`: a second press and hold during Transcribing starts nothing; one transcribe call, one insert.
- `esc_right_after_release_does_not_cancel_the_transcription` and `esc_while_transcribing_is_ignored_and_the_text_still_inserts`: Esc cancels only while recording (as the M1.1 coordinator defines it); once the key is released the text still goes in. Flagged for the Lead in case that isn't the intended UX.
- `a_denied_microphone_on_press_never_records`: `PermissionMissing(Microphone)`, no Recording, no prompt (Denied, not NotDetermined); granting it makes the next dictation work.
- `a_transcriber_error_then_a_successful_dictation`: error, then the next dictation inserts.
- `shutdown_while_transcribing_never_inserts`: an abandoned transcription that answers after shutdown inserts nothing.

Stale-result guard: no public path leaves Transcribing or Inserting without a result (Cancel applies only while recording, and shutdown ends the task), so the job-id guard is defensive and no integration test can reach it. The Developer's unit test `pipeline::tests::a_late_transcript_from_an_earlier_dictation_is_never_inserted` does exercise it: without the `job == self.job` arms, the late `Transcribed(1, "stale")` arriving in Transcribing would become `Insert("stale")`, move the state to Inserting and fail `assert_eq!(runner.state, State::Transcribing)` (and the final `["first", "third"]`). Reasoned from the code; product code not edited.

Privacy (from reading the code): the only `info!` is `dictation failed` with the `DictationError` Display, which carries engine or insert error strings, never a transcript. The per-step `debug!` uses the `Event`/`Command` Debug, which prints `TranscriptReady { len }` and `Insert { len }` (#32, unit-tested in core). No log-capture test: `tracing-subscriber` isn't a dev-dependency and `Cargo.toml` is outside the Tester's edit list. Minor follow-up: `TranscribeError::Network`/`Engine` strings reach the info log, so the real engines (M2/M3) must keep response bodies out of them (tech-debt issue).
