## Criterion 4: first-time user in a freshly restored `dictation-vm-2`
Each part started from a fresh restore of the golden image. The microphone grant was removed with `tccutil reset Microphone com.dictationapp.desktop`. The app was launched with the test flags (`--debug-provider-url` to T4a's local provider, `--debug-audio-file` tone as the microphone, `--debug-onboarding`), because the VM has no microphone and a made-up key must not go to Groq. I drove the window with the e2e `ax.js` helpers (the `cua-vm` MCP server dropped its connection mid-run, so I used the same cua-driver in the VM over ssh) and clicked system prompts with the driver's foreground click. Only the VM was driven.

Part A (no permissions at all):
1. Launch: window "Set up dictation-app" at Step 1 of 4, "Allow the microphone". Log: `onboarding shown at launch step=Microphone`.
2. "Allow microphone" raised the real macOS prompt (`1-microphone-prompt.png`). I clicked Allow; the log shows `microphone prompt answered granted=true` and the window moved to Step 2 by itself.
3. Step 2, "Continue" with Accessibility not granted: refused, stayed on Step 2.
4. Closed the window mid-way, tray "Set up dictation…": reopened at Step 2 (`onboarding opened from the tray step=Accessibility`).
5. "Open System Settings" opened Privacy & Security, Accessibility with dictation-app listed and off (`2-accessibility-system-settings.png`), and the window then showed "Relaunch to finish" with a Relaunch button.
6. **Not possible:** turning dictation-app on asks for the VM user's password (`3-accessibility-password-sheet.png`). I did not guess a password, so I could not do a live re-grant, and so could not see the step advance by itself or what a running app picks up (the answer for #50 is in the PR's `docs/ENGINEERING.md` change, which I did not re-verify live).
7. Relaunch pressed with Accessibility still off: the app restarted (new pid), log `relaunching for onboarding`, then `onboarding shown at launch step=Accessibility ... resumed: true`, window back on Accessibility, microphone still granted. Note the relaunched app has none of my test flags, as a person's would not.

Part B (freshly restored again; the golden image has the app's Accessibility grant, so only the microphone was reset):
1. Mic prompt, Allow: the window moved to Step 2 showing "Accessibility is allowed." with Continue. It did not advance by itself, because it was already granted when the step was shown; Continue moved on to Step 3 (see minor below).
2. Step 3 "Add your API key": closed mid-way and reopened from the tray: same step.
3. Made-up bad key, "Test and continue": "rejected this API key", still on Step 3, provider saw `auth=bad` (401), no key saved.
4. Made-up good key: moved to Step 4 "Try it", provider saw `auth=good`.
5. A dictation (Right Option hold from the VM's Terminal, the tone as audio): the provider replied 200, the transcript `hello world` landed in the window's field, the window said "It works.", Done hid the window. The provider had 3 requests: bad, good (the Test), the dictation.

## Untested behaviour found
- **Minor, test gap:** removing `state === "granted" &&` from the auto-advance in `refresh()` (`src/Onboarding.tsx`) fails no Vitest test: a permission going from not-determined to denied would call `goTo` for the next step. The app's `go_to` still refuses it (and `each_step_is_reached_only_when_the_ones_before_are_done` covers that), so the user can't actually skip a step, but the UI test doesn't pin its half. I added no test (product-side file list); to be filed as a `tech-debt` issue.
- **Minor, UX:** when a permission step is first shown already granted (a user who granted it earlier, or the golden image), it says "Accessibility is allowed." and waits for Continue instead of moving on. Matches the spec's "advances when newly granted" and is not a failure.
