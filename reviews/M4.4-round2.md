## New finding

### R3 — Major: timed-out keychain reads accumulate live worker threads

Location: `src-tauri/src/engine.rs:166`–`:185` (spawn and timeout);
user-facing trigger: `src-tauri/src/commands.rs:72` (Settings save rebuild).

The timeout bounds the receiver's wait, but does not stop the thread inside
`reader.api_key(provider)`. Its join handle is dropped, and there is no
shared pending-read state or bound preventing the next rebuild from
starting another read. If access remains unanswered, startup leaves one
read alive and every subsequent Settings save adds another. Each retains
its thread and configuration until the underlying call eventually returns
or the process exits. The update mutex serializes waiting rebuilds but is
released on each timeout, so it does not bound these abandoned reads.

Concrete reproduction compiled the **actual, unchanged**
`src-tauri/src/engine.rs` as a module against the workspace libraries, with
a `SecretStore` whose `get` waits on a condition variable and counts active
calls. Four calls to `engine_from_config` with 30 ms deadlines returned
unavailable engines while leaving respectively **1, 2, 3, 4 live reads**
and zero completed reads. They ended only when the fake store was explicitly
unblocked. Separately, two actual
`changed(config, live, |c| c.save_settings(...))` calls using the production
**15-second** deadline returned successfully while leaving respectively
**1 and 2 live reads**. Thus this is a reproducible failure of timeout
cleanup and bounded resource use, not a claim that startup still hangs.

Suggested fix: use a bounded keychain worker/pending-read mechanism shared
across rebuilds, or an OS operation that can be cancelled. A timed-out read
must not allow each Settings save to spawn another blocked OS read. Preserve
provider/settings freshness when a pending operation completes. Add a
regression that repeatedly times out/rebuilds while the store remains
blocked and asserts the number of outstanding reads stays bounded, then
unblocks it and verifies cleanup and recovery.

Reproduction source: `/tmp/m44-r2-engine-repro.rs`; build/run driver:
`/tmp/m44-r2-compile-repro.py`; results:
`/tmp/m44-r2-engine-repro.log`. All keys were explicitly fake and kept in
memory. No product or test file was modified for the reproduction.

## Startup and debug-hook assessment

- Startup creates `KeyPending` and starts the rebuild on a separate thread;
  there is no synchronous keychain read in setup. A dictation before it
  completes reports the pending message, sends no provider request, pastes
  nothing and returns Idle. Existing tests for this behavior passed.
- Dictation snapshots the current engine without taking the rebuild mutex.
  Each save's rebuild reads configuration inside that mutex. An independent
  condition-variable reproduction saved a different fake key while the
  startup read held its earlier snapshot: after startup and the save both
  completed, the last read used the saved key and the active engine was
  remote. No stale final overwrite was observed.
- Timeout, denied access and unavailable keychain produce the clear
  `KeychainUnavailable` error without a key in the message. Timed-out reads'
  later answers are discarded: merely allowing access after the deadline
  does not update the engine; a subsequent Settings rebuild or restart is
  required. The reproduction confirmed this. Worker lifetime is R3.
- `flags::TEST_FLAGS` is `cfg!(debug_assertions)`. Release parsing ignores
  both new key flags; the release-parser regression passed. The set hook
  reads bounded stdin, validates through `Config`, and prints only fixed
  success messages or sanitized errors. Tests for invalid/overlong/non-UTF-8
  input, denied keychain, failed stdin and non-disclosure passed.
- A normal debug launch with a key hook runs it **before** single-instance
  setup and exits, even if another app instance exists; it changes the
  keychain through its own process, without changing the running engine.
  A hook arriving through the existing instance's forwarding callback is
  ignored by `handle_flags`, so that callback neither reads stdin nor
  performs keychain writes/deletes. Release parsing provides no such hook.
- Password transport and host tracing were verified by the fake-password
  suite. The remote `security unlock-keychain` command uses `-p "$pw"`;
  the password is therefore an argument to that short-lived VM process,
  although it is absent from the host/SSH argument strings and traces.
  The broad helper comment claiming no password in any VM process list is
  stronger than the implementation; this is the disposable VM login password,
  not the API key, and is not a new blocking finding.
