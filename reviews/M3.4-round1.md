## Findings

Four major findings; no blockers or minors. These are reproducible settings correctness and error-handling defects; no secret disclosure was found.

### 1. Major: saving unrelated settings silently replaces the existing model

**Location:** `src/Settings.tsx:171`.

Every Save sends `model: info.defaultModel`, even when the provider has not changed. Load valid Groq settings with `model: "whisper-large-v3"`, change only Language to `de`, and Save: the persisted model becomes `whisper-large-v3-turbo`. The form has no model field or indication that it changed this setting. This loses an existing supported setting and can change transcription quality without the user's choice. The current test covers changing provider, which should reset the model, but does not cover preserving it when the provider stays the same.

**Suggested fix:** retain the loaded model when retaining the loaded provider; select the new provider's default only when the provider changes. Add a settings-only save regression test using a valid non-default model. This does not require adding a model picker.

### 2. Major: an old provider's key-status response can disable testing the current saved key

**Location:** `src/Settings.tsx:55` (also `src/Settings.tsx:96`, `src/Settings.tsx:111`).

`checkKeySaved` commits every response to one shared boolean without checking which provider is still selected. Reproduction: Groq has a saved key; switch to OpenAI, hold its `has_api_key` reply, switch back to Groq and let its `true` reply finish, then deliver OpenAI's `false` reply. Groq now says “No key saved yet.” Clicking Test key shows “Paste your API key.” without calling `test_api_key`, despite the saved Groq key. The inverse order can falsely show “Key saved” for a provider with no key. Different keychain calls run on the blocking pool, so reply order is not guaranteed.

**Suggested fix:** associate responses with both the selected provider and a request generation, dropping obsolete replies (including initial-load and post-save queries). Add delayed, reversed-order `has_api_key` tests for both boolean values and verify that the current saved key remains testable.

### 3. Major: provider changes during Save leave a success message over unsaved settings

**Location:** `src/Settings.tsx:165` (also `src/Settings.tsx:180`, `src/Settings.tsx:222`).

The form inputs remain editable while Save awaits keychain/file operations. Start saving a typed Groq key and hold `set_api_key`; select OpenAI and type its replacement key; then finish the Groq save. The earlier closure clears the newly typed OpenAI key, saves Groq, and sets “Key saved” from Groq's status. Reload updates language/hotkey but never reconciles the provider. The form displays OpenAI with “Settings saved.” and “Key saved”, although the persisted provider is Groq and OpenAI has no saved key. A macOS keychain prompt makes this a practical interaction window. No key is sent to the wrong provider by this reproduction, but the displayed and persisted provider disagree.

**Suggested fix:** prevent edits to the form during Save (for example a disabled fieldset), or track form revisions and reconcile only the snapshot actually saved without clearing newer input or claiming newer edits were persisted. Add a deferred-save test that attempts provider/key edits before completion and checks the displayed provider, actual saved provider, key status, and replacement input.

### 4. Major: keychain lookup errors are swallowed as permanent loading

**Location:** `src/Settings.tsx:55` (also `src/Settings.tsx:57`, `src/Settings.tsx:259`).

If `has_api_key` rejects with “keychain access was denied”, `checkKeySaved` sets `keySaved` to `null`, the same state used for an in-flight lookup. Once the request has finished, the form still says “Checking for a saved key…” indefinitely. Test key then refuses to invoke the backend and asks the user to paste a key because `keySaved !== true`. The backend's clear `keychain` error path is therefore unreachable through the empty-field UI in this case. The error is lost rather than explained, and the user cannot distinguish a blocked keychain from a running check.

**Suggested fix:** represent loading and failed lookup separately, surface a safe keychain/IPC error with a retry path, and consider allowing the stored-key Test command to report its own typed error when presence is unknown. Test both an error result and an IPC rejection from `has_api_key`.
