## Locking, freshness, and panic recovery

- **No waiter/reader lock cycle found.** `in_flight_or_start` releases the
  state mutex before `Read::wait`; the condition-variable wait releases the
  outcome mutex (`engine.rs:214`). Completion takes state then outcome
  (`engine.rs:307`), and no outcome holder subsequently takes state.
  The reader never needs `Transcribers`' rebuild mutex. Thread registration
  happens while holding state, so a fast completion cannot clear the slot
  before it is registered.
- **The post-save rebuild rejects stale answers.** Successful `changed`
  invalidates before rebuilding (`engine.rs:343`); the read compares both
  provider and generation (`engine.rs:259`). A stale pending read finishes
  before a fresh one starts, retaining the bound. Serialized engine updates
  ensure the save's rebuild runs after an earlier startup rebuild. The
  independent save/startup check and the regression that saves after
  startup has already timed out both passed; the latter checks the actual
  outgoing authorization against a local mock server.
- **Reader panic does not wedge the slot.** A separate fake store panicked
  on its first read and returned a fake key on its second. The first build
  returned unavailable in under one second with a two-second deadline;
  the next build returned remote, with exactly two reads total.
  `catch_unwind` converts failure to the fixed error, then clears the slot
  and wakes waiters (`engine.rs:291`). The synthetic panic also invokes
  Rust's normal panic hook; it contains no credentials. Artifacts:
  `/tmp/m44-r3-panic.rs`, `/tmp/m44-r3-compile-panic.py`,
  `/tmp/m44-r3-panic.log`.
