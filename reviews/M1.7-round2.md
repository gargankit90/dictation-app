## Round-1 findings

### R1 (major): fixed

`src-tauri/src/lib.rs:253` starts the pipeline before `listen_for_later_launches` at line 279. `Pipeline::spawn` installs the hotkey sink synchronously before returning (`crates/app/src/pipeline.rs:135`). Initial-launch flags are handled before forwarded flags. Setup does not wait for a secondary, and the forwarding callback needs neither a Tauri main-thread call nor the singleton-state mutex: no new circular wait was found.

The shell now uses `Instance::listen_checked`; failed injection returns `Rejected` (`src-tauri/src/lib.rs:340`). The transport maps rejection to NAK (`crates/platform/src/single_instance/unix.rs:167`), and the secondary returns `InvalidData`; `run` maps acquisition errors to exit 1. ACK still means accepted by the hotkey sink, not completed recording/transcription.

**Round-1 harness rerun:** retargeted `/tmp/m17-review-harness` sources to this worktree in `/tmp/m17-round2-harness`. The unchanged `startup_ack_can_precede_hotkey_start_and_lose_press` still positively reproduces loss with its deliberately old ordering and unconditional `Instance::listen` callback: `Forwarded`, `inject=false`, zero events. That control does not exercise the fixed shell callback and must not be presented as a current-shell failure. Four additional external checks use the current production shell functions extracted verbatim, the production platform module/parser, and real `SyntheticHotkey` with an inert OS source:

- Old early-listener order with the **current shell callback**: NAK before hotkey start; afterward ACK and exactly one `Pressed` at the sink.
- Current startup order: secondary remains unanswered during a 300 ms startup hold; start hotkey, then listener; secondary returns `Forwarded` and sink receives `Pressed`.
- Startup exceeding a shortened 100 ms I/O deadline: explicit `TimedOut`, no automatic duplicate retry. On this macOS run the closed queued connection produced no later event. An already-written frame may be delivered later on other scheduling/transport outcomes; timeout is delivery-uncertain, never successful acknowledgment.
- Directory/lock checks described under R2 below.

All four external checks passed. The first slow-startup probe incorrectly required later delivery and failed because macOS discarded the closed connection's unread data; the final check correctly allows either zero or one late delivery after explicit failure, and rejects duplication. This is a harness expectation correction, not a product change.

**What happens while the pipeline starts:** the socket is already bound, so connected launches wait in its backlog rather than receiving an early ACK. Connection/write/busy failures can retry up to the 5 s forwarding deadline; once a frame is written, waiting for an answer uses the default 2 s I/O timeout. NAK and answer timeout are terminal failures, not retried. Startup longer than that can therefore fail a launch explicitly; a user should not infer non-delivery from timeout. The fix does not promise durable queuing or exactly-once completion, and introduces no unbounded startup wait for the primary.

Production shell test selection: **32/32 passed**, including all four new shell regressions (pre/post-start rejection, no-event launch, queued startup delivery, and transport rejection).

### R2 (minor), tech-debt #96: fixed for the stated scope

`crates/platform/src/single_instance/mod.rs:242` checks the final directory entry with `symlink_metadata`; symlinks/non-directories are refused. Existing group/other permissions trigger chmod to 0700 at line 247; failure aborts acquisition. The lock entry is checked for symlinks before opening at line 184. External checks confirmed 0777 becomes 0700, both directory and lock symlinks are refused, and the lock target remains unchanged. Production regressions cover these cases too.

**TOCTOU/threat-model assessment:** these are path-based checks, not atomic inode pinning. A same-UID process can replace the directory or lock between check and use, and ancestor symlinks are not rejected. Such a process already has authority to connect, inject debug flags, replace the lock inode, or disrupt the primary under the round-1 model; defeating this check adds no demonstrated privilege or access beyond that authority. With the normal trusted per-user cache/temporary parent, another UID cannot replace the private directory or its entries. No new blocker or major follows from the remaining same-UID race. This is not a guarantee for an arbitrary shared writable ancestor or hostile same-UID isolation.

The documentation's ownership language is stronger than the literal metadata check: an already-0700 directory has no explicit UID comparison. A foreign private directory ordinarily fails when opening its lock; a looser foreign directory fails chmod. This does not establish a concrete failure in the supported per-user paths and does not reopen #96 as a new finding. No cross-account or hostile shared-parent test was performed.
