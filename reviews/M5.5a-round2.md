## Earlier findings

**B1 — resolved.** `crates/platform/src/cursor/macos.rs:189` rejects any
ordinary attribute outside the three-item allowlist before making AX IPC.
Neither `AXValue` nor `AXSelectedText` can be requested. `read_field` at
line 341 obtains text only through `AXStringForRange`, with a one- or
two-unit window ending at the selection start. Unsupported, failed and
timed-out range reads return an error; the pipeline pastes without an added
space. Metadata reads (`AXSubrole`, `AXSelectedTextRange`, and the focused
element) do not fetch field text. No alternative whole-field path remains.
An app that disregards the requested range can still return extra data;
the adapter copies at most the requested units and releases that response.
The implementation never asks it for a larger text range.

I regenerated the round-1 synthetic AX harness from this head, replacing
the removed `units_before` entry point with `AxField::string_for_range`.
The original million-unit `AXValue` responder remains available to expose
any fallback; it was never invoked. Real Core Foundation objects and
`CFRelease` were retained, and no real application was queried. Commands:

```sh
python3 /tmp/m55a-round2-build-harness.py
rustc --edition 2024 /tmp/m55a-cursor-harness.rs -o /tmp/m55a-cursor-harness
/tmp/m55a-cursor-harness
```

Both executions exited **0**. The bounded-read run reported:

```text

AXValue rejected before synthetic IPC
```

The recording-field tests independently exercise the complete `read_field`
flow with a million-unit field and three failure types, asserting the
exact bounded request sequence. The allowlist test also verifies refusal
of three non-allowed attributes before IPC.

**M1 — resolved.** `crates/platform/src/cursor/macos.rs:118` checks null
before constructing `Cf`. The original null-path reproduction now returns
`None` and exits **0**, rather than trapping with status 133. Its added
regression test passes against real Core Foundation. Ownership on the
changed paths is sound: `AxField` moves and owns the focused reference;
subrole, selected-range and string Copy results, attribute-name strings,
and the created range parameter have one RAII owner each. Early errors
drop already-owned objects; no null wrapper is constructed. Type checks
precede CF string and AX range access. Returned text units are owned Rust
data, with no borrowed CF reference escaping.

## VM scenario fixes and #140

- `e2e_smart_space.sh` still requires exactly one separating space, no
  leading space in an empty document, and no duplicate existing space.
  Case folding accommodates TextEdit's capitalization without accepting
  wrong spacing or different words. Removing the intermediate document
  read avoids the reported autocorrection hang; the final document is
  still asserted. The log-redaction assertion remains.
- `e2e_layout_paste.sh` still selects each layout, requires every layout
  to be tried, and asserts the exact pasted transcript. Moving the layout
  query after the paste prevents that Terminal query from stealing focus.
  The selected source is checked before activation and after dictation;
  the documented limitation about per-app source behavior remains, as
  does existing issue #136 about discrimination outside Dvorak.
- Explicitly clearing flags in `type-keys.js:53` makes a fixture promising
  unmodified letters send unmodified letters. This is an honest fixture
  correction, but its successful run is **not evidence that production
  paste leaves modifier state clean**.

**#140: unresolved runtime concern, not a demonstrated new blocker.**
`crates/platform/src/insert/macos.rs:339-350` uses the combined-session
source and posts both V down and V up with Command set. It posts no later
modifier-release or flags-cleared event. Apple's installed SDK
`CGEventSource.h` documents that source tables accumulate modifier state
from posted events, so the reported inherited flags are plausible and
deserve the isolated check in [#140](https://github.com/gargankit90/dictation-app/issues/140).
However, the supplied observation followed multiple synthetic event
producers, and neither this review nor that report isolates this app as
the cause or demonstrates a following physical key becoming a shortcut.
Static inspection cannot establish that hardware-key behavior. I did not
post events on the owner's session or use the VM.

I would not classify a confirmed post-dictation shortcut (for example,
typing `h` hiding the focused app) as a cosmetic minor: that is a concrete
user-visible correctness failure. The necessary follow-up is a clean VM
measurement of combined/HID flags before and after one app paste, followed
by an unmodified physical-equivalent key and a source-less synthetic key,
with the other event producers excluded. Until then #140 remains open;
the fixture change neither fixes nor disproves it. No blocking severity
is assigned without the requested concrete attributable failure.
