## Findings by severity

### M1 — major: Secure Input can turn on before the clipboard write and paste

**Location:** `crates/platform/src/insert/mod.rs:213` (check), `:219`
(snapshot), `:223` (write), `:225` (paste).

The probe runs only before saving the clipboard. If the user focuses a
password field during that snapshot, the subsequent write and paste proceed
while Secure Input is on. This breaks the milestone's skip requirement and
can put the dictated text into the password field. The window includes the
whole clipboard snapshot (all items and representations), clipboard write,
and keyboard-layout lookup; it is not limited to the few instructions after
the probe. The 300 ms settle delay happens after sending paste and does not
protect this path.

**Reproduction:** `/tmp/m42-review-probe/src/main.rs` uses the actual
`PasteInserter` with `MemClipboard`, a wrapper whose `snapshot()` turns an
`AtomicBool` Secure Input probe on, and a key sender that records the probe
at paste time. Starting with the probe off, `insert()` returns `Ok(())`, the
transcript is written, and the key sender observes Secure Input on. The
original clipboard is restored afterward, which does not undo the paste.
Starting with the probe on produces `InsertError::SecureInput` and zero
snapshot, write, restore, or key calls, confirming the existing early guard
works. This is a deterministic port-level reproduction, not a new VM focus
experiment. The Lead confirmed during this review that neither the Lead nor
the owner accepted the documented race as an exception to the spec.

**Suggested fix:** retain the initial check, probe again immediately before
`write_dictation`, and probe again immediately before sending the paste
chord (after any potentially slow key-layout preparation). If blocked before
the write, return `InsertError::SecureInput` without changing the clipboard.
If blocked after the write, restore the saved clipboard through the existing
session-marker guard, skip the chord, and return `InsertError::SecureInput`
so the pipeline shows the message and returns to Idle. Preserve the existing
restore-error handling without replacing a newer user copy. Add deterministic
tests that switch the probe during snapshot and after the dictation write,
asserting no paste, appropriate restoration, and recovery on the next
attempt. These checks reduce the avoidable window; the OS does not provide
an atomic focus-check-and-paste operation.

No other blocker, major, or new minor findings. No new tech-debt issues.

### 3. Text filtering and metadata

Trimming uses Rust Unicode whitespace rules and preserves inner text. The
filter matches only a complete trimmed phrase, ignoring ASCII case: no
substring matching, Unicode case folding, internal whitespace normalization,
or punctuation removal. Low-probability "Thank you." is kept, as are longer
speech and Unicode/internal-whitespace variants outside the phrase list.
Empty results are dropped first. Exact stock phrases with a high probability
are deliberately dropped; this remains a heuristic, not a guarantee about
what a person actually said.

Aggregation is the unweighted arithmetic mean of finite segment values,
not their maximum; no segments/all nonfinite values yield `None`. Mixed
NaN/finite values ignore NaN. A direct NaN fails the threshold comparison.
Missing per-segment probability defaults to zero in the existing parser,
which biases toward keeping text. No new provider parsing/error leak found.

The external wiremock probe invoked the real `OpenAiCompat` through
`Transcriber::transcribe_detailed`: segment probabilities 0.8/0.6 produced
0.7 and dropped the phrase; 0.01/0.99 produced 0.5 and kept it; 0.05 kept
clear speech; empty segments produced `None` and kept it. Thus the real
engine overrides the compatibility default and preserves metadata. Engines
using the default report no probability and cannot trigger the silence filter.
