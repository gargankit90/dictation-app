Each invocation verified that one test ran. This reduces concern about the original timeout flake but does not resolve finding 1.
- The whole PR diff changes only this test. Product code, dependencies, guards, and specifications are unchanged.
- The entered channel establishes that a callback is in flight before drop. The handled flag checks callback completion when drop returns, and joining the second launch checks an actual Forwarded result. These remain useful assertions; the release mechanism is the gap.
- Production defaults are correctly stated: io_timeout is 2 seconds and forward_timeout is 5 seconds. A read timeout is Forward::Fail and returns "the running instance didn't answer" immediately; the 5-second retry budget does not extend that read.
- The ordinary pipeline/UI workload is not awaited by forwarded_launch. Injector::inject takes a mutex and calls the registered sink, whose pipeline implementation uses try_send. Thus slow transcription alone should not delay the ACK. However, the PR's claim that only a whole-process stall can cause the error is too absolute: delayed startup before listen, starvation of the relevant reader thread, or callback/logging/lock delays can also exhaust the client's read timeout while other process threads run. The socket is bound before listening starts, so startup backlog time counts too. Describe this as a bounded failure when an ACK is not available within 2 seconds, rather than a guarantee about a busy app. No production timeout change is required by this test-only fix.
