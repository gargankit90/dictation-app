## Findings by severity

### B1 — Blocker: restoring sensitive clipboard content removes its privacy markers

**Location:** `crates/platform/src/insert/macos.rs:113` (also `:37–39`).

`snapshot_items` filters out all three `org.nspasteboard` privacy types, even when they belong to the user's previous clipboard content. For example, if a password manager copied a value with `ConcealedType`/`TransientType`, dictating snapshots its value but discards the protection. Restore then publishes that value as an ordinary new clipboard write, making it eligible for clipboard-manager history/display. This exposes previously protected content even though the transcript write itself is correctly marked. The unit test `our_types_are_never_saved` currently enforces this incorrect treatment of another app's markers.

**Suggested fix:** preserve the original item's privacy representations and restore them with its data. Treat only our private session type as ours; handle any stale own-session snapshot explicitly rather than dropping privacy types from unrelated content. Add a regression using a marked previous item and verify the restored item retains those markers.

**Reproduction:** a `/tmp` harness copied the PR adapter, substituted a private named pasteboard for `generalPasteboard()`, and used fabricated data only. It wrote a text item with all three markers, then called the actual `snapshot()`, `write_dictation()`, and `restore_snapshot_if_unchanged()` implementations. Result:

```text
PRIVACY: restored_text_present=true concealed=false transient=false auto_generated=false
```

### M1 — Major: a copy during restore construction is overwritten

**Location:** `crates/platform/src/insert/macos.rs:205` (construction at `:208–218`, overwrite at `:219`).

The session/change-count check runs before `items_from` allocates and fills every restored `NSPasteboardItem`/`NSData`. A large clipboard therefore creates a substantial interval in which another app can copy, after the check succeeds but before `write_items` unconditionally clears the pasteboard. That new copy is lost and restore incorrectly returns `true`. Existing fake tests copy during the settle delay, before the restore check, so they do not exercise this interval.

**Suggested fix:** build restored items first, then check the session and change count immediately before the destructive write. Keep that final check/write section short and serialize this adapter's own writers. Document the residual cross-process race because AppKit does not provide a compare-and-swap transaction; avoid widening it with data conversion. Add a deterministic regression that replaces the clipboard during reconstruction and expects restore to leave the new copy alone.

**Reproduction:** the same private-pasteboard harness supplied a saved item with 128 MiB across 32 data representations plus a text representation. A competing thread copied fabricated text 8 ms after restore began. The copy completed while restoration was constructing items; the actual restore then replaced it:

```text
RACE: competing_copy_completed=true
RACE: restore_returned=true duration_ms=43 competing_copy_preserved=false
```

This reproduces the avoidable construction window, rather than claiming an atomic external-write guarantee is implementable with NSPasteboard.

### N1 — Minor: worker-thread pasteboard calls lack an autorelease pool

**Location:** `crates/platform/src/insert/macos.rs:193` (also the other Cocoa clipboard entry points).

The pipeline invokes insertion on Tokio's blocking pool, which does not supply a Cocoa autorelease pool. Neither this adapter nor its caller creates one. A `/tmp` worker-thread harness called the actual snapshot implementation 24 times on a private pasteboard with fabricated data. With `OBJC_DEBUG_MISSING_POOLS=YES`, Cocoa emitted 199 missing-pool diagnostics, including `NSPasteboard` and `__NSArrayM` objects reported as “just leaking.” A control wrapping each call in `objc2::rc::autoreleasepool` emitted none. The practical accumulation rate is not established; this is nonblocking rather than a claimed large-data memory leak.

**Suggested fix:** scope the macOS Cocoa operations in local autorelease pools, keeping owned Rust snapshots/retained results alive as needed. [Apple's thread-safety guide, Autorelease Pools](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/ThreadSafetySummary/ThreadSafetySummary.html) describes the per-thread requirement.

Tracked as [tech-debt #79](https://github.com/gargankit90/dictation-app/issues/79).

### Unsafe, threading and layout details

- Carbon FFI matches the installed SDK, including `UniCharCount` as `unsigned long`/`usize`, Command modifier state, no-dead-keys mask, and the four-unit output buffer. The retained TIS source outlives borrowed CFData/layout bytes and is released once by RAII on the main thread. AppKit constants are immutable; objc2 retained objects and protocol conversions maintain ownership.
- `crates/app/src/pipeline.rs:586` calls insertion through `spawn_blocking`. Clipboard I/O and the 300 ms settle run there, outside the audio callback and UI thread. Items are created/read on the caller thread rather than sent between threads. The current pipeline serializes inserts; the trait's broader concurrent-use promise merits care when adding callers.
- `on_main` checks `pthread_main_np` and executes directly on the main thread, avoiding synchronous dispatch to itself. In the external harness, both an inline main-thread call and a worker call serviced by a running CFRunLoop returned on the main thread; both real current-layout lookups selected key code 9 without sending any event. This supplements the repository test that checks only the thread predicate.
- [Apple documents](https://developer.apple.com/documentation/dispatch/dispatchqueue/sync%28execute%3A%29-3segw?language=objc) that sync dispatch waits for completion and targeting the current queue deadlocks. A busy main thread delays this lookup; an indefinitely blocked/non-draining main loop would hang it. No current main-thread wait on insertion was found in setup/shutdown, so there is no additional concrete deadlock finding. Do not add one when extending this call path.
- Checked Command+layout-V selection, Dvorak and uppercase fake cases, ANSI fallback and Windows virtual-key convention. CGEvent flags encode the chord on the V down/up pair; no synthetic events were posted during review. Accessibility fails at insert as described in the PR, returning through the pipeline's insert-failure path.
