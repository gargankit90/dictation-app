## Findings

### 1. Major: overlapping saves corrupt the settings file

**Location:** `crates/app/src/config.rs:94` (write and rename at lines 95–96);
concurrent callers are enabled by `src-tauri/src/commands.rs:31` and `:50`.

Every call opens and truncates the same `settings.json.tmp`, without a lock.
Two blocking-pool tasks can open that inode before either renames it. Their
writes overlap, and one task can rename the inode into `settings.json` while
another still holds a writable handle to it. Different-length JSON documents
can leave trailing bytes, so subsequent `get_settings` calls fail to parse
the persisted settings. Other saves fail with a missing temporary-file error
after another task renames their shared path. This needs no crash or second
app instance: two overlapping invocations suffice.

**Reproduced on macOS using the actual public `Config::save_settings`:** an
external Rust harness under `/tmp/m33-review-probe` depended on this checkout's
core, ports and app crates and supplied a no-op `SecretStore` (no keychain
access). For each of 100 rounds, eight threads shared one `Arc<Config<_>>`,
waited on a barrier and saved valid settings whose model alternated between
one and 100 `x` characters. After joining the threads, the harness parsed the
final file through `settings::from_json`. Of 800 save calls, 665 returned an
error; 26 rounds left malformed JSON. The first malformed file contained a
complete short settings object followed by the tail of the longer object.
The reproduction wrote only synthetic settings into a temporary directory
and removed that directory afterward.

**Suggested fix:** give each save an exclusively created, unique temporary
file in the destination directory, finish and close its write, then atomically
replace the destination and clean up failures. Alternatively, serialize the
entire write/rename transaction for all callers of a path; account for multiple
`Config` objects targeting that path. Add a concurrency regression test using
different-length valid documents that asserts every save succeeds and readers
always see one complete valid document. Keep validation before any write.

**Crash semantics:** same-directory rename gives a single writer atomic
replacement on macOS, preserving the old destination until rename. It does
not make the shared-inode race above safe. No file or directory sync is done,
so the current implementation also does not promise durability across power
loss; distinguish that from atomic replacement in the documentation.
