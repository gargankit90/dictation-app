## Detailed checks

### CoreAudio patch and real-time ownership

Reviewed `1389a2d..4480ddd` separately from the vendored release. All **19** corresponding pristine vendor files compared byte-for-byte with the local crates.io 0.14.2 source; **0 mismatches**. The product patch is confined to the input callback owner/wrapper and its tests, with PATCHES.md and the adapter's dependency explanation. It preserves the upstream output callback and data conversion paths.

`third_party/coreaudio-rs/src/audio_unit/render_callback.rs:53`: InputBuffer owns the original data pointer, actual Vec capacity and one-buffer AudioBufferList. Logical mDataByteSize never substitutes for capacity during destruction. Keeping the original pointer also avoids relying on any pointer AudioUnitRender may write back. The added raw-pointer operations have SAFETY comments, and the normal input wrapper now only restores pointer/length, renders, constructs borrowed callback args and calls the existing consumer. No new allocation, mutex, logging, stream-format query, or Arc cloning occurs in that wrapper's callback. The oversized path uses one relaxed atomic increment and returns before render. Miri validates the pure ownership/resize/drop path; allocator instrumentation validates the HAL wrapper's size changes and destruction.

`render_callback.rs:141` and `:740`: allocation uses the largest current buffer, maximum-frames-per-slice, reported device range and 4096-frame floor. Queries happen during callback setup. Client stream format is set by cpal before callback installation and remains fixed for the unit; device-native changes do not authorize changing the client's buffer layout. The patch removes the dangerous callback-time format query rather than accepting a new layout without changing its data-view type.

**Oversized means lost audio, not recovered audio:** that entire callback block is omitted, with no silence padding or later replay. At 48 kHz, a 4097-frame callback would omit about 85 ms. The next fitting callback can proceed with the same allocation. The added counter is currently unread by handy-recorder/the app, so it is not included in stopped.dropped_frames and no app warning is promised for this path. The intentionally conservative preallocation plus explicit error return is a memory-safe, nonblocking fallback, not a claim of lossless capture for arbitrary callback sizes. Actual capture and unusual-device behavior remain hardware validation work. Vendored-test CI coverage is already tracked in #88.

### Device identity, delay and teardown

`crates/platform/src/audio/macos.rs:95`, `:377`: the query is Option-returning throughout. Inspected pinned handy-cpal's default_input_device and Device::id: failed CoreAudio property reads return None/Err; a null UID becomes an error; its NonNull unwrap follows a non-null check. Thus no-default/read-failure does not panic in this path. Unknown default keeps a nonfailed warm device; an already failed recorder still reopens. Query occurs before the shared recorder lock and runs on the audio worker's blocking pool. No device enumeration/open, stream initialization or permission prompt is introduced by the query itself.

Independent **1000-query** measurement: warm median **15 µs**, p99 **140 µs**, maximum **388 µs**. First process query was **77.112 ms**, including HAL startup. This is measured evidence on this Mac, not a hard CoreAudio latency guarantee; cold HAL work is off the executor and normal warm starts avoid it. Active recording keeps its opened device until Stop, as documented and tested.

`macos.rs:176`, `:303`: delay mirrors the pinned handy-recorder/rubato construction and is computed once at open, not on the callback thread. Collector drops only leading valid frames, carries the remaining skip across chunks, and keeps the flushed tail. A 16 kHz device skips zero. A replacement recorder supplies its own delay. `crates/app/src/pipeline.rs:395` moves source ownership into final spawn_blocking so both normal and panic unwinding destruction occur there.

### Queue policy, cancellation and permission race

`crates/app/src/pipeline.rs:235`: pending Start+Discard collapse without touching that device; repeated Discard coalesces. A preceding discard for the currently open session is retained. Since core permits one recording, and a Stop blocks progress to the next dictation until its result, the maximal reachable queue is Discard/Start/Stop. Closing atomically stops acceptance and takes pending commands out of the queue; dropping pending Stop senders releases waiters. No mutex is held across an await or audio operation. Notify retains a permit across the empty-check/wait boundary. Drop also closes the worker if its runner unwinds.

`pipeline.rs:126`, `:174`, `:567`: try_send never blocks the hotkey sink; the atomic overflow signal produces an Esc after the next consumed key. Checked the actual Mac matcher: it forwards matched hotkey edges and first Esc presses, suppressing repeats; unrelated typing does not fill this channel. A normal hold/release contributes two keys, far below 64. Filling it requires synthetic input or prolonged scheduler/port unresponsiveness; no normal-dictation cancellation was established. Existing synchronous permission work has no hard latency guarantee, so the comment's human-rate claim should not be read as an absolute scheduling proof. Overload deliberately cancels rather than risking a dropped release leaving capture active. The subsequent normal-dictation regression passes.

`pipeline.rs:534`: shutdown remains first, followed by start failures and job completions. Their production rate is bounded by serialized audio/single active job; keys cannot starve them. After each key, a ready Tick is taken without waiting, preserving the recording limit even while keys stay ready. Captured Stop receivers and job/session guards prevent a stale source error from failing a newer recording.

`pipeline.rs:365`, `:651`: PermissionDenied is retained for the corresponding Stop, which returns it without calling source.stop. Immediate failure while Recording takes the discard/Idle route; failure after Release reaches the audio job and generates PermissionMissing while Transcribing. The session filter suppresses the other notification, preventing duplicates. `crates/core/src/coordinator.rs:122` adds exactly one production transition: Transcribing + PermissionMissing → error/Idle. Inserting and other state/event behavior are unchanged.
