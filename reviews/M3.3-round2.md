### Transaction, locking and failure handling

At `crates/app/src/config.rs:105`, validation and serialization precede all
filesystem changes. Lines 108–126 hold the same guard across directory
creation, exclusive file creation, the entire write, sync and rename. There
is one lock acquisition and no recursive save or other lock acquisition in
this path, so there is no internal lock cycle. Normal returns and unwinding
drop the guard. `PoisonError::into_inner` at line 111 reacquires the protected
unit even after a panic; it does not permanently disable saving. The poison
flag remains set, but subsequent saves use the same recovery path.

Lines 114–118 derive each temporary path from the destination's parent and
combine process ID with an atomic sequence shared by calls. Concurrent
Config instances in one process get distinct sequence numbers; concurrent
processes have distinct process IDs. `create_new(true)` at line 183 prevents
truncating an existing file. `write_new` writes all bytes, syncs and drops its
file handle before the rename at line 120. The rename stays on the same
filesystem and publishes a complete document. Readers do not need the mutex.

Lines 121–123 attempt temporary-file removal on write, sync or rename errors,
then return the original I/O error. Cleanup is best effort if removal itself
fails; a process crash or panic before rename can also leave an unpublished
temporary file, without modifying the published settings document. The
documentation correctly distinguishes file sync from directory durability:
the directory is not synced, so this is not a guarantee of the latest save
surviving power loss.
