## Findings

### R1 — major: wait for settings before accepting key-step input

**Location:** `src/Onboarding.tsx:176` (late provider assignment at line 179;
silent load failure at lines 177 and 182; conditional provider save at line 278).

The key step renders enabled provider/key controls before `getSettings()` has
answered. Its eventual reply unconditionally replaces the provider without
clearing the typed key. A first-time user can select OpenAI and paste an OpenAI
key while that request is pending; when the default Groq settings arrive, the
provider switches back to Groq but the password input retains the OpenAI key.
Pressing **Test and continue** then invokes `test_api_key` with `provider: groq`
and that OpenAI key. This sends a credential to a different provider from the
one the user chose and prevents the intended setup from succeeding.

The failed-load variant also breaks setup: errors are silently discarded and
`settings` stays null. Selecting OpenAI and successfully testing/saving its key
then skips `saveSettings` entirely. Groq remains selected in the backend, so
the real `set_onboarding_step(try)` refuses with **Add a working API key first.**
despite the successful OpenAI test. Retrying Test repeats this; returning to
the key step is required to retry loading settings, with no explanation of
the actual problem.

**Reproduced outside the repository:** `/tmp/m52-review-probes.py` copies the
unchanged frontend into `/tmp/m52-review-probes` and adds two mockIPC probes.
The first defers `get_settings`, selects OpenAI and types a made-up key, then
resolves the request with default Groq settings and clicks Test. The recorded
test command uses **groq**, failing the expected **openai** assertion. The
second rejects `get_settings`, selects OpenAI and tests successfully: the key
is saved for OpenAI, there are **zero** `save_settings` calls, the backend
provider remains **groq**, and the step remains **key**. The copied test
backend uses a generic permission error for refused steps; the real Rust
`NotYet(Step::Key)` message is the working-key error quoted above. No real
credentials or network calls were used. Output:
`/tmp/m52-review-probes/delayed-replies.log`.

**Suggested fix:** make settings loading an explicit state. Keep provider/key
editing and Test disabled until settings are loaded; show a load failure with
a Retry action instead of swallowing it. Never overwrite an edited provider
with a stale reply. Require loaded settings before testing/saving/advancing,
and add delayed-reply and failed-load regression tests checking the provider
sent to Test, provider persistence, and successful progression after retry.
